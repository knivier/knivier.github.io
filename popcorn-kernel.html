Operation map

How Popcorn boots and runs in the v0.7 tree. UEFI (BOOTX64.EFI) or GRUB Multiboot2 loads the kernel, asm enters long mode, kmain / init bring up memory and Rust drivers, then the shell runs over the display and keyboard drives.

Reference

Layout 
Popcorn/
├── scripts/          # core.sh, popcorn_build/, QEMU helpers
├── src/
│   ├── link.ld
│   ├── core/         # C + asm kernel
│   ├── rust/         # popcorn_kernel crate
│   ├── uefi/         # BOOTX64.EFI loader
│   ├── pops/         # remaining C pops (Dolphin)
│   └── includes/
└── target/           # build outputs

Only the linked ELF (and UEFI loader) run in the guest. Scripts are host-side.

Boot 
UEFI: BOOTX64.EFI → handoff → kernel
GRUB: Multiboot2 ISO → ELF @ 0x100000 → start

start (kernel.asm)
  identity / direct map
  long mode
  kmain → init → shell

CI runs test-uefi on both UEFI and GRUB smoke paths.

Init order 
init / kmain bring-up (typical)
  multiboot / UEFI tags
  memory_init (PMM + VMM)
  idt + PIC
  rust_init → driver registry + screen/kbd/…
  timer + scheduler
  pops register
  console handoff → shell

Display drawing is Rust (tty0/fb0). Console UX stays in C as a client.

Syscalls 
open, read, write, close, ioctl
gettime, sleep, yield
malloc / free (heap)
getcwd / chdir (where wired)

Device calls go through the drive registry. Full ring-3 ABI is still ahead.

Caveats

v0.7 is pre-1.0. User processes and full isolation are not done.

Internal disks stay locked until an explicit install unlock.

Scheduler still uses bootstrap guards around early PIT ticks.
